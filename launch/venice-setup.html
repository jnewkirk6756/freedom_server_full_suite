Venice activation.

A real provider connection needs more than a polished room. This staging host does not accept keys, run private accounts or perform inference.

1 · Keep the key server-side

Add a Venice-issued VENICE_API_KEY privately to the intended backend’s Render secrets/environment group. The OpenAI key from Freedom is not a Venice key. Do not enter either key in this page, chat, a character bio or GitHub.

2 · Deploy the authenticated private candidate

The full source includes deploy/render-venice.yaml, private login, an allowlist, session/ownership checks, persistent-storage requirements and turn limits. It is separate from this public preview. Applying that template creates paid resources; choose a hosting and API budget first.

3 · Check the current catalog

Run npm run venice:preflight for presence-only checks, then npm run venice:catalog on the private server. The catalog command uses authenticated GET requests; it does not generate a reply or video. Pin supported text, voice and video models, and review their privacy classification.

4 · Verify a bounded real session

After approving API usage, sign in to the private client and test a short synthetic text turn first. Enable microphone and photos only through separate explicit consent. A provider refusal stays a refusal; no hidden fallback provider is called.

5 · Connect the house context

The private text endpoint accepts roomContext: {roomId: "bedroom", enabled: true}. Only named room presets reach the provider. Room lighting, tone and suggested pace are fictional scene settings—not body readings or permission changes. Entering a room makes no paid request by itself.

Video jobs: quote → approve cost → queue → retrieve → review → save → replay locally. A scene change does not regenerate media.

Current status: staging online does not mean Venice is live. Check host status in the Venice tab; a secret-presence flag alone is not an authentication or inference test.
